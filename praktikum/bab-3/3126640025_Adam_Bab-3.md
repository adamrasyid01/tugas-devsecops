## BAB I PENDAHULUAN

### 1.1 Latar Belakang

Dalam ekosistem *cloud-native* dan praktik DevSecOps, aplikasi modern jarang sekali berjalan sebagai monolit tunggal dalam satu container. Aplikasi umumnya dipecah menjadi arsitektur layanan berlapis (*multi-tier architecture*), yang terdiri dari *reverse proxy/web server*, *application backend*, dan *database*. Pemisahan ini menuntut adanya mekanisme komunikasi jaringan antarkomponen yang terisolasi, pengelolaan persistensi data yang andal, serta orkestrasi siklus hidup (*lifecycle*) container secara terpadu.

Docker menyediakan abstraksi jaringan (*networking*) dan penyimpanan (*storage mounts*) untuk menjawab tantangan tersebut. Melalui *user-defined bridge network*, container dapat saling berkomunikasi secara aman menggunakan resolusi DNS internal tanpa perlu membuka port ke publik. Di sisi persistensi, pemilihan antara *Named Volume*, *Bind Mount*, dan *tmpfs* menentukan bagaimana integritas data, portabilitas lingkungan, serta keamanan host dijaga. Selain itu, Docker Compose hadir sebagai *declarative application model* yang menyatukan seluruh dependensi, volume, network, dan *healthcheck* ke dalam file konfigurasi terpusat. Praktikum Bab 3 ini bertujuan untuk memberikan pemahaman teoritis serta pengalaman praktis dalam membangun, mengonfigurasi, dan mengamankan aplikasi *multi-container* berbasis Docker Compose.

### 1.2 Tujuan

1. Membuat dan mengonfigurasi *user-defined bridge network* serta membuktikan *automatic DNS name resolution* antarkontainer.
2. Membedakan karakteristik, persistensi, keamanan, dan kasus penggunaan dari *Named Volume*, *Bind Mount*, dan *tmpfs mount*.
3. Menerapkan skenario *backup* dan *restore* data pada *named volume* secara aman menggunakan container pembantu (*helper container*).
4. Menulis dan mengonfigurasi *Docker Compose* untuk aplikasi multi-tier (Nginx sebagai *reverse proxy*, Flask sebagai *app backend*, dan PostgreSQL sebagai *database*).
5. Mengimplementasikan *service dependency* dengan *healthcheck* (`condition: service_healthy`) guna menjamin *readiness* layanan.
6. Mendiagnosis kendala *build/startup* serta merumuskan analisis risiko keamanan dan rekomendasi perbaikan untuk lingkungan *production*.

## BAB II LANDASAN TEORI

### 2.1 Docker Network dan User-Defined Bridge

Jaringan container pada dasarnya membentuk *reachability graph* (graf keterjangkauan) antarkomponen. Secara default, Docker menyediakan *default bridge network*. Namun, untuk aplikasi multi-container, penggunaan **user-defined bridge network** sangat dianjurkan karena menyediakan:
- **DNS Resolution Otomatis:** Container dapat saling memanggil menggunakan nama container (*container name*) atau *service name*, bukan IP dinamis yang rentan berubah ketika container di-restart.
- **Isolasi Lingkungan yang Lebih Kuat:** Container di luar network tersebut tidak dapat menjangkau service internal secara langsung, menciptakan *security boundary* antara tier frontend, backend, dan database.
- **Konfigurasi Fleksibel:** Subnet dan gateway dapat dikonfigurasi secara eksplisit (misal: `172.20.0.0/16`).

Port publishing (`-p HOST_PORT:CONTAINER_PORT`) membuat aturan NAT/iptables pada host. Berdasarkan prinsip *least privilege* dan *least exposure*, port database (5432) atau backend internal tidak boleh dipublikasikan ke host jika hanya dibutuhkan oleh service internal dalam network yang sama.

### 2.2 Lifecycle Data dan Storage Mounts (Volume, Bind Mount, tmpfs)

Container bersifat *stateless* dan *ephemeral*, di mana lapisan *writable layer* akan musnah saat container dihapus. Docker menyediakan tiga mekanisme mount utama:

| Tipe Mount | Lokasi Penyimpanan | Persistensi | Tingkat Ketergantungan Host | Kasus Penggunaan Utama |
| :--- | :--- | :--- | :--- | :--- |
| **Named Volume** | Dikelola Docker (`/var/lib/docker/volumes/`) | Persisten (tetap ada saat container dihapus) | Rendah (Agnostik OS) | Database (PostgreSQL, MySQL), data aplikasi permanen |
| **Bind Mount** | Path direktori/file spesifik pada host | Persisten (mengikuti file di sistem host) | Tinggi (bergantung path host) | *Live development*, file konfigurasi (`nginx.conf`) |
| **tmpfs Mount** | Memori host (RAM / swap) | Non-persisten (hilang saat container stop) | Terikat Linux/RAM | File sensitif sementara, token, cache, session |

### 2.3 Docker Compose sebagai Model Aplikasi Deklaratif

Docker Compose mengotomatisasi definisi dan eksekusi stack multi-container melalui file `compose.yaml` (atau `docker-compose.yml`). Compose menyatukan konfigurasi:
- `services`: Komponen komputasi (image, build context, port, environment).
- `networks`: Segmentasi jaringan (misalnya `frontend` dan `backend`).
- `volumes`: Deklarasi volume terkelola untuk persistensi data.

Perintah operasional utama meliputi `docker compose up -d` (menjalankan stack di background), `docker compose ps` (memantau status), `docker compose logs` (melihat log konsolidasi), `docker compose down` (menghentikan dan membersihkan container/network), serta `docker compose down -v` (menghapus container beserta volume data).

### 2.4 Service Dependency, Healthcheck, dan Readiness

Perintah `depends_on` standar hanya mengontrol urutan inisiasi proses container, namun tidak menjamin bahwa proses di dalam container sudah siap menerima koneksi (misalnya PostgreSQL masih melakukan inisialisasi tabel). Dengan menambahkan **healthcheck** dan parameter `condition: service_healthy`, Compose menahan startup container aplikasi hingga database benar-benar siap (*ready state*), mencegah terjadinya kegagalan *connection refused* saat aplikasi dinyalakan.

### 3.6 Analisis Wajib dan Troubleshooting

#### 1. Masalah yang Muncul dan Metode Diagnosis

**Permasalahan:**
Saat menjalankan proses build/up pada Docker Compose, proses build service `app` mengalami kegagalan (*failed to solve / build error*) pada step `COPY requirements.txt .`.

![Error saat compose up](img/error%20saat%20compose%20up%20karena%20tidak%20ada%20requirements.png)

*Gambar 3.13: Pesan kegagalan build Dockerfile akibat file requirements.txt tidak ditemukan.*

**Diagnosis & Penanganan:**
- **Analisis Pesan Kesalahan:** Error log menunjukkan `failed to compute cache key: failed to calculate checksum of ref ...: "/requirements.txt": not found`.
- **Akar Masalah:** Dockerfile menginstruksikan `COPY requirements.txt .`, namun file dependensi `requirements.txt` belum dibuat pada direktori context `./app`.
- **Tindakan Solutif:** Dibuat file `requirements.txt` pada folder `./app` yang berisi paket dependensi yang dibutuhkan:
  ```text
  flask
  psycopg2-binary
  ```
- Setelah file ditambahkan, perintah `docker compose build --no-cache` dan `docker compose up -d` dieksekusi ulang dan stack berhasil terpasang sempurna.

#### 2. Risiko Keamanan dan Operasional Relevan

1. **Pemaparan Port Berlebih (*Unnecessary Port Exposure*):**
   Mengekspos port database (5432) ke host (`0.0.0.0:5432`) membuka celah brute-force dan eksploitasi dari jaringan luar. Dalam praktikum ini, database diisolasi murni di network `backend` tanpa port mapping ke host.
2. **Keleluasaan Modifikasi pada Bind Mount:**
   Bind mount tanpa opsi `:ro` (*read-only*) memungkinkan proses container yang terkompromi memodifikasi atau menghapus file penting pada host.
3. **Penyimpanan Kredensial Plaintext di File Compose:**
   Menyimpan `POSTGRES_PASSWORD: labpass123` langsung pada file YAML berisiko membocorkan rahasia jika file masuk ke public repository (Git).
4. **Risiko Kehilangan Data akibat `docker compose down -v`:**
   Perintah `down -v` menghapus volume beserta datanya secara permanen. Tanpa cadangan rutin, data stateful akan hilang seketika.

#### 3. Rekomendasi untuk Lingkungan Production-Like

- **Implementasi Docker Secrets:** Alihkan penyimpanan password database dari environment variable ke Docker Secrets atau Secret Manager eksternal (HashiCorp Vault / AWS Secrets Manager).
- **Least Privilege User:** Konfigurasikan Dockerfile backend dan database agar berjalan menggunakan user non-root (`USER appuser`).
- **Resource Limiting (cgroups):** Tetapkan batas pemakaian CPU dan memori pada setiap service di compose file (`deploy.resources.limits`) untuk mencegah serangan *Denial of Service* (DoS).
- **Prosedur Otomasi Backup Volume:** Terapkan cron job terjadwal untuk snapshot dan backup data volume PostgreSQL ke penyimpanan off-site/cloud storage terenkripsi.
- **TLS/SSL Encryption:** Pasang sertifikat SSL/TLS pada Nginx sebagai reverse proxy ingress agar seluruh komunikasi publik terenkripsi (HTTPS).

## BAB IV EVALUASI DAN LATIHAN MANDIRI

**1. Mengapa user-defined bridge lebih baik daripada default bridge untuk multi-container app?**
> User-defined bridge menyediakan resolusi nama domain (DNS) otomatis antar container berdasarkan nama service/container, sedangkan default bridge mengharuskan penggunaan IP manual atau flag `--link` yang sudah deprecated. Selain itu, user-defined bridge memberikan isolasi lingkungan jaringan yang lebih tersegregasi dan aman.

**2. Apa risiko bind mount terhadap keamanan host?**
> Bind mount memberikan akses langsung container ke sistem berkas host. Jika container berjalan dengan hak root dan mount tidak diset sebagai `read-only` (`:ro`), container yang disusupi penyerang dapat menimpa file sistem host, menyisipkan malware, atau mencuri file konfigurasi sensitif host.

**3. Apa perbedaan `docker compose down` dan `docker compose down -v`?**
> `docker compose down` hanya menghentikan dan menghapus container serta network proyek, namun mempertahankan named volume data. Sebaliknya, `docker compose down -v` secara destruktif turut menghapus seluruh named volume yang dideklarasikan di file compose beserta data di dalamnya.

**4. Kapan `depends_on` dengan healthcheck lebih tepat daripada `depends_on` biasa?**
> Saat service downstream (seperti web backend) membutuhkan service upstream (seperti database atau message broker) dalam status benar-benar siap melayani kueri (*ready to accept connections*). `depends_on` biasa hanya menunggu container dibuat/dijalankan, bukan kesiapan layanannya.

**5. Bagaimana strategi backup volume untuk database produksi?**
> Pada lingkungan produksi, strategi backup yang ideal adalah:
> - Melakukan logical dump terjadwal (misal: `pg_dump` untuk PostgreSQL) guna memastikan konsistensi data transaksional.
> - Menyimpan snapshot file terenkripsi ke penyimpanan eksternal (seperti Amazon S3 / Object Storage).
> - Melakukan uji restore (*restore drill*) secara berkala untuk memvalidasi integritas data cadangan.

## BAB V KESIMPULAN

Praktikum Bab 3 berhasil memperkuat pemahaman mengenai konsep fundamental networking, mekanisme persistensi data, dan orkestrasi aplikasi multi-container pada Docker. Berdasarkan pengujian yang telah dilakukan, dapat disimpulkan bahwa:
1. **User-Defined Bridge Network** merupakan fondasi krusial bagi komunikasi mikroservis yang aman dan dinamis melalui dukungan automatic DNS service discovery.
2. Pemilihan tipe penyimpanan harus disesuaikan dengan kebutuhan: **Named Volume** untuk data persisten database, **Bind Mount** untuk sinkronisasi kode dan konfigurasi host, serta **tmpfs** untuk data sementara berbasis memori.
3. **Docker Compose** mempermudah deklarasi arsitektur multi-tier (*Nginx-Flask-PostgreSQL*) secara terstruktur dan terkelola dalam satu siklus hidup terpadu.
4. Penerapan **Healthcheck** menjamin *readiness* layanan dan mencegah *race condition* ketergantungan antar-service saat aplikasi diinisiasi.
5. Aspek DevSecOps seperti network segmentation, manajemen secret yang aman, pembatasan hak akses mount, dan mitigasi risiko operasional merupakan prasyarat mutlak sebelum menerapkan container stack pada lingkungan produksi.
