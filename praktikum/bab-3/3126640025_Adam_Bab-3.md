### 3.6 Analisis Wajib dan Troubleshooting

#### 1. Masalah yang Muncul dan Metode Diagnosis

**Permasalahan:**
- Masalah: Saat mengakses curl http://localhost:8080/static.html, halaman tidak muncul (respon bukan halaman yang diharapkan). Nginx hanya melayani file yang benar-benar ada di direktori html/ yang di-bind mount, sedangkan static.html belum dibuat di folder tersebut.
- Diagnosis: Dengan curl -i http://localhost:8080/static.html terlihat kode status respon dari Nginx (404/error), dan pemeriksaan pada direktori html/ menunjukkan bahwa file static.html memang tidak ada, sehingga Nginx tidak dapat menemukan file yang diminta untuk disajikan.
- Solusi: Membuat file static.html di dalam folder html/. Karena direktori tersebut di-bind mount (./html:/usr/share/nginx/html:ro), file langsung dapat diakses tanpa rebuild image, dan curl http://localhost:8080/static.html kemudian berhasil menampilkan halaman tersebut.

#### 2. Risiko Keamanan dan Operasional Relevan

1. **Pemaparan Port Berlebih (*Unnecessary Port Exposure*):**
   Mengekspos port database (5432) ke host (`0.0.0.0:5432`) membuka celah brute-force dan eksploitasi dari jaringan luar. Dalam praktikum ini, database diisolasi murni di network `backend` tanpa port mapping ke host.
2. **Keleluasaan Modifikasi pada Bind Mount:**
   Bind mount tanpa opsi `:ro` (*read-only*) memungkinkan proses container yang terkompromi memodifikasi atau menghapus file penting pada host.
3. **Penyimpanan Kredensial Plaintext di File Compose:**
   Menyimpan `POSTGRES_PASSWORD: labpass123` langsung pada file YAML berisiko membocorkan rahasia jika file masuk ke public repository (Git).
4. **Risiko Kehilangan Data akibat `docker compose down -v`:**
   Perintah `down -v` menghapus volume beserta datanya secara permanen. Tanpa cadangan rutin, data stateful akan hilang seketika.

#### 3. Rekomendasi untuk Lingkungan Production-Like

- **Implementasi Docker Secrets:** Alihkan penyimpanan password database dari environment variable ke Docker Secrets atau Secret Manager eksternal (HashiCorp Vault / AWS Secrets Manager).
- **Least Privilege User:** Konfigurasikan Dockerfile backend dan database agar berjalan menggunakan user non-root (`USER appuser`).
- **Resource Limiting (cgroups):** Tetapkan batas pemakaian CPU dan memori pada setiap service di compose file (`deploy.resources.limits`) untuk mencegah serangan *Denial of Service* (DoS).
- **Prosedur Otomasi Backup Volume:** Terapkan cron job terjadwal untuk snapshot dan backup data volume PostgreSQL ke penyimpanan off-site/cloud storage terenkripsi.
- **TLS/SSL Encryption:** Pasang sertifikat SSL/TLS pada Nginx sebagai reverse proxy ingress agar seluruh komunikasi publik terenkripsi (HTTPS).

## BAB IV EVALUASI DAN LATIHAN MANDIRI

**1. Mengapa user-defined bridge lebih baik daripada default bridge untuk multi-container app?**
> User-defined bridge menyediakan resolusi nama domain (DNS) otomatis antar container berdasarkan nama service/container, sedangkan default bridge mengharuskan penggunaan IP manual atau flag `--link` yang sudah deprecated. Selain itu, user-defined bridge memberikan isolasi lingkungan jaringan yang lebih tersegregasi dan aman.

**2. Apa risiko bind mount terhadap keamanan host?**
> Bind mount memberikan akses langsung container ke sistem berkas host. Jika container berjalan dengan hak root dan mount tidak diset sebagai `read-only` (`:ro`), container yang disusupi penyerang dapat menimpa file sistem host, menyisipkan malware, atau mencuri file konfigurasi sensitif host.

**3. Apa perbedaan `docker compose down` dan `docker compose down -v`?**
> `docker compose down` hanya menghentikan dan menghapus container serta network proyek, namun mempertahankan named volume data. Sebaliknya, `docker compose down -v` secara destruktif turut menghapus seluruh named volume yang dideklarasikan di file compose beserta data di dalamnya.

**4. Kapan `depends_on` dengan healthcheck lebih tepat daripada `depends_on` biasa?**
> Saat service downstream (seperti web backend) membutuhkan service upstream (seperti database atau message broker) dalam status benar-benar siap melayani kueri (*ready to accept connections*). `depends_on` biasa hanya menunggu container dibuat/dijalankan, bukan kesiapan layanannya.

**5. Bagaimana strategi backup volume untuk database produksi?**
> Pada lingkungan produksi, strategi backup yang ideal adalah:
> - Melakukan logical dump terjadwal (misal: `pg_dump` untuk PostgreSQL) guna memastikan konsistensi data transaksional.
> - Menyimpan snapshot file terenkripsi ke penyimpanan eksternal (seperti Amazon S3 / Object Storage).
> - Melakukan uji restore (*restore drill*) secara berkala untuk memvalidasi integritas data cadangan.

## BAB V KESIMPULAN

Praktikum Bab 3 berhasil memperkuat pemahaman mengenai konsep fundamental networking, mekanisme persistensi data, dan orkestrasi aplikasi multi-container pada Docker. Berdasarkan pengujian yang telah dilakukan, dapat disimpulkan bahwa:
1. **User-Defined Bridge Network** merupakan fondasi krusial bagi komunikasi mikroservis yang aman dan dinamis melalui dukungan automatic DNS service discovery.
2. Pemilihan tipe penyimpanan harus disesuaikan dengan kebutuhan: **Named Volume** untuk data persisten database, **Bind Mount** untuk sinkronisasi kode dan konfigurasi host, serta **tmpfs** untuk data sementara berbasis memori.
3. **Docker Compose** mempermudah deklarasi arsitektur multi-tier (*Nginx-Flask-PostgreSQL*) secara terstruktur dan terkelola dalam satu siklus hidup terpadu.
4. Penerapan **Healthcheck** menjamin *readiness* layanan dan mencegah *race condition* ketergantungan antar-service saat aplikasi diinisiasi.
5. Aspek DevSecOps seperti network segmentation, manajemen secret yang aman, pembatasan hak akses mount, dan mitigasi risiko operasional merupakan prasyarat mutlak sebelum menerapkan container stack pada lingkungan produksi.
